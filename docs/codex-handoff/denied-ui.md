# 閲覧・操作不可時のUI

状態: 確定した方向性を画面ごとに整理。v0.9で一通り実装したのはBoard閲覧不可であり、Room / Thread / Responseまで完成したわけではない。

## 共通原則

- 「発見」制限は廃止済み。閲覧できないことだけを理由に一覧から対象の存在を消さない。
- SummaryItem上段に「閲覧不可」、中央にTitle、下段に更新日時を表示する。
- Itemはクリック可能。詳細Paneで閲覧できない理由を確認できる。
- 保護する本文や子一覧をサーバーから返し、CSSで隠すだけの実装にしない。
- Headerや閉じる操作は残し、行き止まりから元のWorkspaceへ戻れるようにする。
- Policy全体の説明と、「今の利用者が満たしていない条件」の説明は別。後者には満たした許可条件や該当しない不可条件を並べない。
- 拒否理由に出す条件自体の公開範囲・ラベルが機密になるケースは未整理。対象の保護本文をラベルやプレビューへ混ぜない。

## Room閲覧不可

合意した画面案:

1. SummaryItemからRoomPaneを開ける。
2. Thumb、Feedback、Profileを非表示にする。
3. 機能ボタンをグレーアウトし、そこからMemberやBoardなどへ進めない。
4. Popup / Dialogに閲覧条件の説明を表示する。
5. Popupを閉じ、RoomPaneを閉じれば元の画面へ戻れる。

Roomの参加条件を全部表示する「参加不可Dialog」と混同しない。このPopupの主題はRoomを**閲覧できない理由**。

後の共通方針に合わせ、不足している許可条件と該当した不可条件を理由として示す。Popupを閉じた後の再表示導線、毎回自動表示するか、グレーアウトしたボタンから理由を再表示するかは未決。RoomOwnerの閲覧救済をどこまで設けるかも、Boardの現行例外から自動的にコピーして確定扱いしない。

## Board閲覧不可

v0.9の具体的な確定要件:

- SummaryItemに「閲覧不可」、Board名、更新日時を残す。Thread数は表示しない。
- Board詳細Paneへ遷移可能。
- Bodyには不足している許可条件と該当した不可条件だけを表示。
- 詳細情報、Policy全体、Thread一覧、Thread作成UIは返さない。
- RoomOwnerは誤設定を修正できるようにBoardを開ける。ただしThread作成条件まで無条件に通るわけではない。

理由文の例:

```text
「Board名」を閲覧できません。
以下の必要条件を満たしていません。
[条件グループA] [条件グループB]
また、以下の閲覧不可条件に該当しています。
[不可グループC]
```

該当しない段落は表示しない。許可条件そのものが空なら、満たす条件が存在するかのように案内せず「現在、閲覧可能な条件が設定されていません」と区別する。

## Thread閲覧不可

- SummaryItemには「閲覧不可」、Title、更新日時を表示し、クリック可能にする。
- Thread詳細PaneのHeaderと閉じる操作を残す。
- #1も#2以降も表示しない。返信入力欄も表示しない。
- Bodyは閲覧条件・不可理由の説明とする。

現行共通テンプレートの「このThreadは閲覧できません。」だけでは、条件を示す将来仕様は完成していない。

Thread件数・Response件数、配置行のRoom / Collection / Board名、FieldやInterfaceのメタ情報のうち、閲覧不可時にもどこまで公開するかは個別の詳細未決。BoardのThread数非表示要件を参考にできるが、すべて合意済みと扱わない。

## Response閲覧不可

ResponsePolicyに閲覧制限を持たせる構想はある。一方、個別投稿の代替表示、投稿番号、作者・時刻、件数、AccountPageのResponse履歴への反映はまだ詰めていない。

「一つのResponseが不可ならThread全体を不可にする」「不可Responseは番号ごと消す」などを確定仕様として実装しない。ThreadPolicyの閲覧判定との関係も実装前に整理する。

## 返信できないとき

不可説明をすべてDialogへ統一する案は撤回している。**TextAreaと送信ボタンが出る位置へ、角丸ボーダーで囲んだ説明を常時表示**する。

文言の合意案:

```text
「ThreadTitle」には書き込めません。
以下の条件が必要です。
[不足している許可条件A] [不足している許可条件B]
また、以下の不可条件に該当しています。
[該当する不可条件C] [該当する不可条件D]
詳しくは「ThreadTitle」のPolicyを確認してください。
```

- 満たしている許可条件は表示しない。不可条件も該当するものだけ。
- Policyへの導線では全体条件を確認できるようにする。
- 閲覧そのものが不可なら返信不可説明まで本文と一緒に出さず、先に閲覧不可画面として扱う。
- ユーザーは以前の表示に「ちょっと問題あるがPolicyを詰めるまで保留」としている。現行表示を最終UXとして固定しない。

ANDグループ内の一部だけ不足している場合のラベル粒度、ORの選択肢を「すべて必要」と誤読させない文言は再確認が必要。共通評価器が返す未成立グループ全体と、「不足する原子条件だけ」の表示は同じではない。

Thread作成不可については、作成ボタンを非表示にする従来方針でもよいとして詳細を保留した。その後のv0.9現行Boardではdisabledボタンになっている。不可ボタンやDialogへ一律統一する合意はない。

## Room参加不可

通常状態の表示:

- Owner: `Owner`（操作不可）。
- Owner以外の参加者: 退会操作。現行表記は`退会`。
- 参加可能な非参加Account: `参加`。
- Guestなど参加不可: **押せる**`参加不可`で理由Dialogを開く。

Guest参加不可はRoomPolicyではなくNiixyのルール。Accountがないと参加状態を保持できないため、PolicyでGuestを許可しても参加できない。

参加不可Dialogは両方を載せる:

```text
Niixyのルール
  GuestはRoomに参加できません。参加状況を保持するAccountがないためです。

RoomAのPolicy
  RoomAへ参加するには、以下の条件を満たす必要があります。
  [条件A] [条件B] ...
```

GuestだからRoom条件を省略すると「Account登録だけで必ず参加できる」と誤認するため、公式ルールとRoomの必要条件を併記するという合意。Room参加Policyの不可条件も扱う際の具体的な文言は追加で整える。

現行はRoom参加Policy未実装なので「Room独自の参加条件はありません」と表示している。将来も常に条件なしと表示する仕様ではない。

汎用Dialog部品自体は残し、必要なところで利用する。ただし参加・閲覧・返信・作成を、同じギミックで実装する必要はない。
